# Iroha v0.4.1 cache and aggregation plan

> Status: implementation complete; release gates and local k3s verification pending
>
> Date: 2026-08-14
>
> Decision record: [ADR 0004 — Cache correctness and report reads](../adr/0004-cache-correctness-and-report-reads.md)

## Goal

Make repeated day, month, year, and cross-domain report reads cheap while preserving Iroha's canonical-data-first contract.

The release target is not “add a cache everywhere.” It is:

    canonical write commits
      -> dependency invalidation succeeds
      -> first read computes from canonical data
      -> repeated identical reads are cache hits

The cache is disposable. Postgres canonical records remain authoritative.

## Current evidence

The v0.4 audit established the following:

| Area                         | Current state                                 | 0.4.1 action                               |
| ---------------------------- | --------------------------------------------- | ------------------------------------------ |
| Domain GET reads             | 24-hour lazy cache with namespace generations | Preserve and harden                        |
| Metric day/month/year series | Cached under read_metrics                     | Repair key identity and write invalidation |
| Daily and sleep aggregates   | Cached after first request                    | Preserve                                   |
| Direct expense list/detail   | Explicitly uncached                           | Preserve                                   |
| Monthly report               | Explicitly uncached                           | Cached lazily under read_reports           |
| 12-month report series       | Recomputes all requested months               | Cached lazily under read_reports           |
| Durable aggregation job      | No handler or active schedule                 | Do not add in 0.4.1                        |
| Canonical daily tables       | Imported health facts                         | Do not reinterpret as generic rollups      |
| Cache backends               | Backend-neutral facade; Postgres default      | Valkey/Postgres parity and k3s smoke test  |

The current report generator calls the complete monthly pipeline once per month in the requested series. The default 12-month request therefore repeats the movement, sleep, daily-health, media, and
expense work twelve times. The existing live measurement was roughly 320 ms for a cold/repeated uncached 12-month request, which is acceptable at current scale but not a sufficient future guarantee.

## Implementation status

The implementation is landed on the release branch. The shared runtime cache module now provides Postgres, Valkey, and `none` backends behind one generation-aware contract; there is no production
process-memory backend. Report reads use `read_reports`, canonical mutation paths invalidate dependent namespaces after commit, failed invalidation causes a degraded-namespace bypass, and Postgres
cleanup is bounded and scheduled as worker maintenance. The deterministic performance fixture and gate are also wired into `make release-candidate`.

The remaining status is evidence, not design: run the complete release gates, record the benchmark, verify both cache modes where the environment permits, and deploy the candidate to local k3s.

## Scope

### In scope

- report response caching for monthly and 12-month report-series requests;
- complete cache identity with effective timezone and version boundaries;
- post-commit dependency invalidation;
- expense metric-series freshness after create, replace, and delete;
- activity route freshness after geocode refresh;
- media/report freshness after media resolution;
- generation-safe cache population;
- degraded-namespace bypass when invalidation fails;
- bounded Postgres cache cleanup;
- deterministic large-fixture performance evidence;
- ADR, glossary, API/request-cache documentation, tests, release candidate, and local k3s verification.

### Explicitly out of scope

- a new yearly cross-domain report endpoint;
- a durable daily/monthly/yearly aggregate table;
- a clock-only “aggregate yesterday” job;
- Telegram, Suzuran, or another delivery client;
- stale-while-revalidate;
- frontend API-shape changes;
- currency conversion or cross-domain scoring;
- changing canonical date or timezone semantics.

## Non-negotiable invariants

1. Canonical Postgres data is the source of truth.
2. A cache miss always falls back to a canonical loader.
3. A failed canonical write never invalidates a namespace.
4. A successful canonical write invalidates after commit.
5. A known invalidation failure bypasses the affected cache namespace.
6. Cache keys contain every response-affecting interpretation.
7. A response loaded under generation N cannot be stored under generation N+1.
8. Missing data remains missing or empty; caching must not turn it into zero.
9. Monthly and yearly metric reducers retain their existing metric-specific algebra.
10. No frontend route calculates a complete lifetime or report aggregate from paginated rows.

## Target architecture

    canonical Postgres tables
            |
            +--> canonical mutation coordinator
            |       |
            |       +--> commit
            |       +--> dependency invalidator
            |
            +--> domain/report service
                    |
                    +--> cache-aside read middleware
                            |
                            +--> current namespace generation
                            +--> complete logical cache identity
                            +--> Valkey or Postgres disposable response

The report service remains synchronous. No report job or report table is introduced by this release.

## Cache contract

### Namespaces

The final private read namespaces are:

| Namespace       | Responses                                      | Freshness dependency            |
| --------------- | ---------------------------------------------- | ------------------------------- |
| read_briefing   | Briefing and overview reads                    | Imported canonical data         |
| read_activities | Activity lists, details, summaries, and routes | Activities and route enrichment |
| read_sleep      | Sleep lists, aggregates, and details           | Sleep canonical records         |
| read_daily      | Daily rows and aggregates                      | Daily canonical facts           |
| read_media      | Media lists, details, and resolution views     | Media canonical records         |
| read_metrics    | Metric catalog and day/month/year series       | All metric source domains       |
| read_reports    | Monthly and 12-month cross-domain reports      | All five report domains         |

Every namespace uses the same backend-neutral cache contract. Callers do not construct Valkey patterns or Postgres cache rows.

### TTL and population

- TTL remains 24 hours.
- Only successful, non-empty JSON 200 responses are stored.
- The first request after invalidation computes synchronously.
- Repeated exact requests return HIT.
- Failed responses are never stored.
- There is no prewarming in 0.4.1.

### Logical key

The logical key must be generated from:

1. method;
2. normalized path;
3. canonical query encoding;
4. effective timezone for date-sensitive routes;
5. response representation version;
6. metric aggregation version where applicable.

The cache key version must be bumped when the effective-timezone contract is introduced. A request without a timezone parameter must still use the configured server timezone in its logical identity.

Report keys must distinguish at least:

- monthly month;
- series end month;
- requested series length;
- effective timezone;
- report representation version.

### Generation-safe population

The runtime cache facade should expose a generation-aware read/write path for the HTTP middleware. The expected behavior is:

    read generation N
    read key at generation N
    load canonical response on miss
    write only if namespace is still generation N

Valkey and Postgres stores must implement the same behavior. The existing simple Get/Set facade may remain for callers that do not need race protection, but report and domain HTTP reads must use the
generation-aware path.

### Degraded namespace behavior

The invalidator performs bounded retries after a canonical commit. If invalidation still fails, it marks the namespace degraded in the running application. The read middleware bypasses that namespace
until a later invalidation succeeds.

Cache backend failures on ordinary reads continue to fail open to canonical loaders. Degraded state is specifically for the case where old cached data may still be reachable after a known write.

## Invalidation matrix

The coordinator must make this mapping explicit and testable:

| Mutation path                                                      | Required invalidation                                         |
| ------------------------------------------------------------------ | ------------------------------------------------------------- |
| Apple Health, GPX, or other activity/sleep/daily import completion | Existing imported-data namespaces, read_metrics, read_reports |
| Media import or connector sync completion                          | read_media, read_metrics when affected, read_reports          |
| Expense create                                                     | read_metrics, read_reports                                    |
| Expense replace                                                    | read_metrics, read_reports                                    |
| Expense delete                                                     | read_metrics, read_reports                                    |
| Media resolution update                                            | read_media, read_reports                                      |
| Geocode refresh                                                    | read_activities                                               |

The invalidation call happens only after the database transaction that changes canonical data succeeds. A no-op idempotent expense retry that does not change a row does not need to invalidate.

## Ordered implementation tasks

### Task 1 — Freeze the contract and fixtures

Create deterministic test data covering:

- two timezones with the same request shape;
- day, month, and year metric series;
- a partial current month;
- an expense create, replacement, deletion, and backdated correction;
- activity route enrichment before and after geocode;
- media resolution changes;
- empty report months;
- at least twelve report months.

Record the expected canonical values and reducer semantics. No fixture may use a frontend-derived aggregate as its oracle.

### Task 2 — Harden runtime cache identity and generations — complete

Likely implementation areas:

- apps/iroha-runtime/cache/cache.go;
- apps/iroha-runtime/cache/postgres.go;
- apps/iroha-server/pkg/httpapi/server.go;
- cache unit and integration tests.

Implement:

- read_reports namespace;
- effective-timezone normalization;
- representation and aggregation version boundaries;
- generation-aware Get/Set behavior;
- old-generation write rejection;
- HIT, MISS, and BYPASS diagnostics;
- parity tests for Valkey and Postgres.

Do not add backend-specific key scans.

### Task 3 — Add the dependency-aware invalidator — complete

Create one application-level invalidation coordinator or equivalent dependency map. Wire it into both API and worker construction.

Update:

- import completion;
- expense create, replace, and delete;
- media resolution mutation;
- geocode refresh;
- media sync/import completion where it does not already pass through import completion.

Add bounded retries, degraded namespace state, structured logs, and counters. Ensure failed canonical writes do not invalidate.

### Task 4 — Cache the report endpoints — complete

Allowlist the existing monthly and monthly-series GET routes under read_reports.

Preserve:

- monthly-report.v1;
- monthly-report-series.v1;
- generated_at semantics;
- empty_months semantics;
- server-owned timezone resolution;
- existing OpenAPI response shapes.

Do not add a yearly report envelope or background report job.

### Task 5 — Repair expense and route freshness — complete

Add regression tests that:

1. request and cache an expense metric series;
2. create an expense;
3. request the same series and assert a MISS/new value;
4. repeat for replace and delete;
5. cache activity routes;
6. complete geocode refresh;
7. assert the route representation is refreshed.

Use canonical API/service responses as assertions, not database-cache internals alone.

### Task 6 — Add bounded Postgres cache maintenance — complete

Add a backend-neutral maintenance entry point with a Postgres implementation that removes:

- expired entries;
- entries from generations no longer current.

Each run must use a bounded batch size and be safe to repeat. Valkey relies on TTL expiry and does not need a delete scan. This task must not create a metric aggregation schedule.

### Task 7 — Add the performance gate — complete; evidence pending

Extend release-candidate evidence with a deterministic larger fixture:

- ten years of daily/activity/sleep/media history;
- at least 100 expenses per month;
- representative empty and partial months;
- twelve-month report-series requests;
- day/month/year metric-series requests.

Measure:

- cold canonical request p50/p95;
- first request after invalidation;
- repeated cache HIT latency;
- database query count and duration;
- cache entry count and TTL;
- report response size.

The durable daily read-model follow-up is opened only if cold p95 exceeds 500 ms or query work is operationally significant. The current release does not create that read model.

Update:

## Acceptance criteria

The implementation is ready for v0.4.1 only when:

- repeated day/month/year metric reads are cache hits;
- monthly and 12-month reports are cache hits after their first request;
- expense mutations refresh derived metric and report responses immediately;
- import/media/geocode mutations refresh their dependent reads;
- no known invalidation failure continues serving the affected old cache namespace;
- effective timezone changes cannot reuse an incompatible response;
- old-generation in-flight responses cannot populate the new generation;
- Postgres cache cleanup is bounded and tested;
- no canonical table or report table was added for this release;
- no yearly report endpoint was added;
- the larger benchmark is recorded;
- make check, make validate, release-candidate, CI, and local k3s verification pass.

## Future gate: durable daily read model

If the performance gate fails, the follow-up plan must define:

- dirty-date tracking for imports and backdated writes;
- a durable derived table with metric, period start, dimensions, observed coverage, aggregation version, and computed source generation;
- sufficient statistics for averages and weighted values;
- rebuild and repair commands;
- report freshness and partial-period semantics;
- migration/backfill and rollback behavior.

That is a separate design. It is not silently included in v0.4.1.
