# Iroha v0.5 quality audit

Date: 2026-09-28

Baseline: `ca1f2b3` (`main`, clean before this audit). This is a read-only source audit of the current Iroha implementation, focused on the private cockpit's shared Grapher UI, owner/admin controls,
Health Auto Export ingestion, and the security boundary around retained raw data. It is not a route-by-route visual sign-off or a deployment review.

## Executive assessment

Iroha has strong foundations: owner-session authentication and CSRF are enforced in the private API router; health intake uses a separate credential; upload and request sizes are bounded; the data
model retains raw evidence for replay; and the non-integration checks are green. The current quality risks are concentrated in sensitive-file permissions and incomplete/quietly dropped health metrics.
The UI is structurally coherent, but its keyboard behavior and rendered accessibility still need a real-browser pass. The bundle has a large client chunk and no written budget yet.

## Quality and performance observations

- `make -C vendor/iroha check` passed: Go format/vet/lint/tests, API contract checks, Python script tests, theme/responsive/motion checks, Svelte formatting/typecheck, and 190 web tests. The output
  includes 97 Python tests and Go unit tests across the workspace.
- `make -C vendor/iroha web-build` passed. The largest emitted client JS chunks were **962.13 kB raw / 250.70 kB gzip** and **471.97 kB raw / 159.90 kB gzip**. This is a measured baseline, not yet a
  confirmed user-visible load defect: initial-route transfer and which chunks each route downloads were not measured. Trace those chunks to dependencies/routes before setting per-entry budgets.
- The current owner-reported integration-test setup is a safety concern: DB-backed tests share the development database and some can remove the dev owner. I did not run `make test-integration` or
  `make release-candidate` because they touch database state. Isolate tests to disposable, uniquely named databases and add a guard that refuses known development databases before making integration
  tests a routine gate.
- The current quality gate does not establish runtime accessibility, visual behavior at 320px/200% zoom, real-device HAE behavior, dependency advisory status, or API latency. Those are open
  measurements, not passed checks.

The repository's earlier release audit (`docs/audits/2026-09-11-v0.5.0-release.md`) is historical evidence, not proof for this current `main` baseline. No live browser server was started, no database
integration tests were run, and no deployment, destructive operation, or release action was performed.

## Recommended order

1. Close the raw evidence permission risk and verify effective volume modes.
2. Reconcile HAE's observed metric inventory; represent unsupported data honestly and preserve replayability.
3. Make integration tests isolated and non-destructive by default.
4. Finish a browser-based Grapher/Admin audit: keyboard and screen-reader flow, light/dark contrast, 320px and 200% zoom, loading/empty/error states, and real seeded data.
5. Attribute the two large client chunks to their importing routes; then record initial-route transfer and establish a bundle budget.
6. Measure API latency under a documented local fixture/workload and add actual version reporting before treating the release quality bar as complete.
7. Reconcile security and theme-architecture documentation with the current implementation.

No source code was changed as part of this audit.

## Follow-up

Commit `cdd96bb` applied the raw-evidence permission fix identified above: the storage directories use `0700`, stored files use `0600`, and tests cover uploads, snapshots, and existing directories. Focused rawfiles tests and `make check` passed after that change. The deployed volume has not been inspected, so its effective modes remain unverified.
