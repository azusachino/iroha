# Iroha v0.5 capability and cut-over inventory

Date: 2026-09-11

Source branch: `feat/v05-sqlx-ddl-cutover`

This is the task-1 inventory for the v0.5 fresh-schema cut-over. The route source and OpenAPI contract remain authoritative for exact request/response details; this document records the keep, replace,
and external-boundary decisions needed for cut-over.

## Consumers and surfaces

| Consumer or surface                           | v0.5 disposition                                                                                                               | Evidence or boundary                                                                                                         |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `iroha-server` private API                    | Keep and extend in `/api/v1`                                                                                                   | Route inventory and OpenAPI are checked together by `pkg/httpapi/api_contract_test.go`.                                      |
| `iroha-job` worker                            | Keep; replace unsafe claim/publication paths with fenced, replayable work                                                      | Durable jobs, leases, schedules, import receipts, and projection refresh remain server-owned.                                |
| `iroha-web` private cockpit                   | Keep all existing journeys; add source attention, coverage/evidence state, connection actions, and report parity               | Routes below are backed by typed shared contracts and the release-candidate browser matrix.                                  |
| `scripts/iroha_cli.py`                        | Keep as the local agent client; add connections, advertised actions, media decisions, statements, metrics, and report commands | CLI remains JSON-first; table output is presentation only.                                                                   |
| `iroha-export-public` and `iroha-public-site` | Keep as a separate sanitized static projection                                                                                 | It consumes no private API/cache response and never writes to this repository.                                               |
| Podman/mise/Make operations                   | Keep the entry points; SQLx is the migration runner                                                                            | A fresh database is bootstrapped and replayed. The legacy database is a comparison/rollback artifact, not an upgrade target. |
| k3s image/deployment consumers                | Keep image names and migration-job invocation contract for the authorized downstream rollout                                   | No deployment or image publication is part of this local cut-over.                                                           |

## Web and public workflows

The private web routes remain: Today, Overview, Activities/detail, Night/Sleep/detail, Daily/Patterns, Media/Library/detail, Expenses, Reports, Metrics, Motion/detail, To-go, Admin, Manual, Dashboard,
and the design workbench. The keep decision includes loading/error/partial states, theme and reduced-motion behavior, stable deep links, and detailed activity route/stream/lap views.

The public workflow remains a separate derived path:

1. `iroha-job` generates sanitized `summary.json`, `activities.json`, `activity-details.json`, `routes.geojson`, and `meta.json`.
2. Schema/privacy validation runs before an atomic temp-directory-then-rename swap.
3. The public builder checks freshness, builds `iroha-public-site`, and serves the static result.
4. A failed export or stale snapshot leaves the previous published volume untouched; no human approval inbox and no repository write credential are introduced.

Local operator commands remain `make dev-up`, `make db-up`, `make db-status`, `make db-logs`, `make db-reset`, `make smoke-local`, `make soak-local`, `make export-public`, `make public-site-build`,
`make release-candidate`, `make check`, `make validate`, and the image targets. The release candidate is the isolated validation path; ordinary public-site generation still requires a compatible
fresh/local database.

## Retained data and cut-over decisions

| Data or state                                                         | Retention/cut-over decision                                                                      | External limit                                                                                                                             |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Raw Apple Health export, GPX, statements, and bounded Health payloads | Preserve bytes with SHA-256 and source receipts; replay into the fresh schema                    | A new export or device payload is required when the source no longer exposes a historical interval.                                        |
| Source instances, receipts, interpretation snapshots, observations    | Retain as provenance and replay authority; never use worker completion order as source authority | Provider timestamps and declared scope determine what can supersede an older interpretation.                                               |
| Canonical activities, routes, samplings, laps, sleep, daily metrics   | Rebuild from retained evidence with stable IDs where identity rules permit                       | Unsupported source detail remains explicitly unavailable; no synthetic measurements are created.                                           |
| Media library/state/history/events                                    | Retain snapshots, dated changes, exact events, and matching decisions separately                 | AniList/Bangumi API history limits are surfaced as source limitations, not invented events.                                                |
| Expense accounts, statements, rows, transactions, corrections         | Retain source statement evidence and account/currency/refund semantics                           | Monthly statement arrival is late data, not a reason to assign receipt time as occurrence time.                                            |
| User-authored matching decisions and task state                       | Preserve through replay and rollback; decisions are inspectable and undoable                     | A user/device action is still required where automatic matching cannot be made safely.                                                     |
| Read revisions, coverage assertions, cache entries                    | Revisions and coverage are durable; cache is disposable and rebuilt by revision                  | A cache miss is acceptable; a stale revision is not.                                                                                       |
| Legacy database                                                       | Keep only as comparison/rollback evidence until owner sign-off                                   | No legacy-schema migration, backfill, or SQLx marking is performed. Post-cutover writes require replay/export if rollback is later needed. |
