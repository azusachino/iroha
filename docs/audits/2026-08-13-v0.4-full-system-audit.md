# Iroha v0.4 full-system audit

> Status: complete primary audit; independent Sol pass aborted at quota checkpoint
>
> Audit target: code and product state at `c48e7de` on `docs/iroha-v0.4-expense-ledger-plan`
>
> Scope: the whole Iroha system from approved product design through database, APIs, ingestion, CLI, frontend, theme registry, tests, images, and k3s delivery. This is not a branch-diff-only review.

## Purpose

This audit determines whether Iroha v0.4 is coherent and releasable as the deterministic central personal-data cockpit that was approved. It traces design decisions into real implementation behavior,
records confirmed defects and unverified risks separately, and ends with explicit release gates and a corrective sequence.

No implementation or deployment changes are part of the audit itself. The prepared `v0.4.0-dev.20260813.03` images remain undeployed while the audit is in progress.

## Contract baseline

The audit treats the following owner decisions as authoritative where older planning text conflicts:

- Iroha owns deterministic canonical storage and stable APIs. OCR agents, Telegram, and Suzuran are external clients, not workflow layers inside Iroha.
- The expense web page does not edit canonical fields. Canonical correction APIs may exist for trusted clients; the approved v0.4 documents still permit a deliberate delete action in the private
  viewer.
- Expenses use typed canonical fields: date, category, amount in minor units, currency, optional merchant/note, and optional item lines.
- There is no expense candidate, revision, or mutation workflow model.
- Reports are monthly only and cover every supported Iroha data domain. Iroha returns report data to requesting clients; it does not own scheduled Telegram delivery.
- The web UI has no report-timezone control. Server-side period semantics remain deterministic.
- Domain-shaped canonical tables remain the source of truth. A stable metric catalog and series/read-model API sits above them.
- The frontend consumes server-derived aggregates and series rather than rebuilding domain aggregation from raw records.
- Data representation is chart-first, with details below, and truthfully exposes missingness, coverage, source, unit, and methodology.
- All registered design-language identities and adopted design-composition identities are shared-registry assets. They may change representation, but not metric meaning, privacy, missingness, or
  errors.
- Shared period controls preserve route-specific needs. `Lifetime` replaces `All year(s)`; Motion retains its combined sport/year/month behavior; monthly pages use month navigation; left/right
  keyboard movement is supported.
- Expense categories have stable, meaningful colors.
- Navigation must scale as new domains and metrics are added.
- The local CLI supports multiple data types, not only expenses.
- Public/private data boundaries and idempotent ingestion are release-critical.

## Method

Four independent fresh-context Sol reviews at xhigh reasoning were launched to cover:

1. product architecture and design traceability;
2. backend, database, API, security, and domain correctness;
3. frontend, UX, data representation, and the theme registry;
4. delivery, quality engineering, operability, and repository standards.

At the owner's quota-conservation checkpoint, all four were instructed to stop and return immediately. None returned a usable report before termination. No finding in this document is attributed to
Sol, and no unreturned conclusion was inferred. The primary reviewer completed the source trace directly. A later fresh-context adversarial pass remains useful after quota renewal but is not a hidden
prerequisite for understanding the confirmed defects below.

Severity means:

- **Critical:** data loss/privacy breach or the central product cannot safely operate.
- **High:** release-blocking incorrect behavior, broken core workflow, or serious contract violation.
- **Medium:** meaningful product/operability gap that can ship only with explicit acceptance and follow-up.
- **Low:** bounded quality or maintainability issue with little immediate user impact.

### P-01 — instant-valued metric series use the wrong timezone date

Severity: **High**

`apps/iroha-server/pkg/metricseries/service.go:549-550` creates a new midnight with `value.Year()/Month()/Day()` and merely labels it with the requested location. It does not convert an instant with
`value.In(location)`. Activity and media bucketing both use this helper at `service.go:246-259` and `service.go:426-438`. An activity at `2026-08-31T16:00:00Z`, for example, belongs to September in
Asia/Tokyo but is bucketed as August.

This violates the explicit per-domain rule in `docs/plans/2026-08-12-periodic-reports.md:501-504`: activities and media use instant conversion, while expense, sleep, and daily fields use calendar-date
semantics. Existing metric-series tests use UTC examples (`apps/iroha-server/pkg/metricseries/service_test.go:91-100` and `:208-216`), so they cannot detect the defect.

Smallest correction: split instant bucketing (`value.In(location)`) from calendar-date bucketing (preserve civil year/month/day), then add positive and negative offset tests crossing both a day and
month boundary.

### P-02 — MonthNavigator's arrow-key behavior is dead code

Severity: **High**

`packages/iroha-shared/src/MonthNavigator.svelte:43-55` defines `handleNavigatorKeydown`, but the component never binds it. The only key handler actually registered is the window-level Escape handler
at `:58`; the root at `:60` has no `onkeydown`. Expenses and reports both rely on this component (`apps/iroha-web/src/routes/expenses/+page.svelte:293` and
`apps/iroha-web/src/routes/reports/+page.svelte:210`).

This directly fails the control contract at `docs/plans/2026-08-12-iroha-data-cockpit-implementation.md:525-538`. No component or browser test exercises MonthNavigator keys.

Smallest correction: bind the handler at the navigator root, add focused component/browser tests for ArrowLeft, ArrowRight, Escape, and input/select exclusion, and verify both consuming routes.

### P-03 — the monthly report's analytical visuals are expense-only

Severity: **High**

The report controller obtains the five-domain report at `apps/iroha-web/src/routes/reports/+page.svelte:32-38`, then fetches only `expenses.amount_minor` and `expenses.count` series at `:41-56`. Its
entire analytical view model at `:117-182` is spending total, category, currency, and expense count. Every registry-owned report theme charts that same expense trend and/or category breakdown;
movement, sleep, daily health, and media appear only in the shared detail-card component `apps/iroha-web/src/lib/components/ReportDetails.svelte:24-150`.

This contradicts the approved report order—headline cross-domain comparison and primary charts before exact domain details—at `docs/plans/2026-08-12-iroha-data-cockpit-implementation.md:595-608`, as
well as the six cross-domain report orientations at `:619-628`.

Smallest correction: define one unit-safe visual model for each available domain plus a cross-domain state/coverage overview; keep incompatible units in separate panels or normalized non-magnitude
signals. Theme components should choose hierarchy and chart grammar from that shared truthful model.

### P-04 — metric discovery navigates to a route that ignores the metric

Severity: **High**

`apps/iroha-web/src/lib/components/CommandPalette.svelte:60-69` converts every catalog metric into `/patterns?metric=<id>`. The Patterns controller imports only legacy daily list/aggregate APIs and
parses only `gran`, `month`, and `year` (`apps/iroha-web/src/routes/patterns/+page.svelte:1-49`); it never reads `metric` or calls the metric-series API. The palette also has no search input—it
renders the complete command list at `CommandPalette.svelte:101-115`.

Consequently metric discovery is a dead-end as the catalog grows. It violates the navigation design and `MetricSearch` acceptance at
`docs/plans/2026-08-12-iroha-data-cockpit-implementation.md:641-701`.

Smallest correction: either make Patterns a real catalog-driven metric viewer whose URL selects a metric, or point catalog results to a dedicated metric route; add actual filtering/search and a
direct-link browser test.

### P-05 — expense/report period and filter state is not URL-addressable

Severity: **Medium**

The expense route initializes month and filters only in local state (`apps/iroha-web/src/routes/expenses/+page.svelte:46-48`) and its month handler only assigns/reloads at `:139-142`. The report route
behaves the same at `apps/iroha-web/src/routes/reports/+page.svelte:21` and `:67-70`. Neither route reads or writes search parameters.

This breaks direct links, refresh restoration, and browser back/forward, despite the URL-state and direct-period requirements in `docs/plans/2026-08-12-iroha-data-cockpit-implementation.md:540-548`,
`:585-593`, and `:630-639`.

Smallest correction: make validated `month`, `currency`, and `category` search parameters the route state, using replace/push consistently and covering direct load plus browser history.

### P-06 — the expense ledger silently drops records after the first 50

Severity: **High**

`apps/iroha-web/src/routes/expenses/+page.svelte:59-66` requests `limit: 50` and stores only `page.items`. The controller ignores `has_more` and `next_cursor`, and the page exposes no next/load-more
behavior. Charts may still show the complete server aggregate while the "exact ledger" below silently omits records.

Smallest correction: retain pagination state and expose deterministic load-more or cursor navigation, including a visible record count/incomplete-list marker. Test a month with more than 50 records.

### P-07 — closed: category colors are category-stable

Severity: **Medium**

Expense categories are still sorted by amount at `apps/iroha-web/src/routes/expenses/+page.svelte`, but the shared BarChart now resolves each categorical datum through
`packages/iroha-shared/src/category-color.ts` before falling back to the theme palette. `food` therefore retains its semantic token when rank or filters change.

The stable semantic category-color requirement is now satisfied; focused category-color tests remain the regression guard.

Follow-up: extend browser assertions across registered languages and adopted composition specimens as those routes gain production coverage.

### P-08 — closed: representation primitives are wired into report UI

Severity: **Medium**

`MetricMetadata.svelte`, `MetricTable.svelte`, `MetricPanel.svelte`, and the CSV helpers are now used by the package-owned report compositions. The obsolete app-local `report-view.ts` was removed;
report DTOs, section helpers, comparison, coverage, facts, cards, charts, and receipts are shared under `packages/iroha-shared`.

The report route now follows the chart/table/provenance/download contract in `docs/plans/2026-08-12-iroha-data-cockpit-implementation.md:484-523`.

The expense route now has the equivalent shared contract: canonical expense DTOs/view helpers, CSV serialization, ledger, and all six registered compositions are package-owned. Remaining work is
route-state truthfulness and the remaining detail-family compositions.

### P-09 — partial request failures can combine new records with stale charts

Severity: **High**

The expense loader assigns the newly requested list at `apps/iroha-web/src/routes/expenses/+page.svelte:58-66` before awaiting 20+ metric requests at `:67-125`. Its catch at `:132-136` records an
error but does not clear series from the previous selection. The report loader similarly assigns the new report at `apps/iroha-web/src/routes/reports/+page.svelte:36-38`, then awaits expense series at
`:41-56`; its catch at `:57-64` preserves prior trend series.

After a month/filter change, one failed series request can therefore render a new ledger/report alongside an old chart, which is worse than an explicit unavailable state and violates the truthfulness
contract.

Smallest correction: load into a request-scoped result and commit state atomically, or model each panel's period/status explicitly and clear stale series on failure. Guard against out-of-order
responses from rapid navigation.

### P-10 — the general CLI still lacks existing-domain resources

Severity: **High**

The CLI parser exposes only `expense`, `report monthly`, and read-only `metric` commands (`scripts/iroha_cli.py:315-387`). It has no activity, sleep, daily, media, raw-file, or import resource. This
conflicts with the stated in-scope "general local Iroha CLI ... and read access to existing canonical domains" at `docs/plans/2026-08-12-expense-ledger.md:87-93`, although the same document later
defers those wrappers at `:211-214` and `:240-242`.

This is both an implementation gap and an unresolved spec contradiction. The owner's later decision that the local CLI support several data types resolves the product intent, but the exact v0.4
resource set still needs to be frozen.

Smallest correction: select a minimal useful set of stable existing-domain read and/or import wrappers, document exact commands and response preservation, and add transport tests. Do not invent
unstable write APIs merely to make the CLI look general.

### P-11 — release gates do not execute the tests that cover runtime failures

Severity: **High**

`Makefile:126` defines `validate` as `check build web-build`; DB-backed tests are a separate target at `Makefile:47-48`, and visual checks are separate at `Makefile:94-96`. CI invokes only
`make check` (`.github/workflows/ci.yml:17-33`). The visual script checks only the caller's selected theme/routes and captures screenshots (`apps/iroha-web/scripts/visual-check.sh:4-7` and `:22-32`);
it has no exhaustive six-theme matrix or product-data assertions. Registry tests merely assert route presence at `apps/iroha-web/src/lib/themes/registry.test.ts:155-163` rather than distinct
identities or behavior.

This explains how compile/unit gates remained green while metric requests, keyboard controls, empty charts, and theme demos failed in the deployed stack. It also falls short of Gate C and Gate D at
`docs/plans/2026-08-12-world-in-data-cockpit-rework.md:251-264`.

Smallest correction: add a release-candidate target that starts an isolated DB, seeds boundary/missing/multi-domain fixtures, runs integration tests, serves the production web build, and executes a
browser matrix for six themes × critical routes × light/dark. Keep the ordinary pre-commit gate fast.

### P-12 — current design documents disagree with the latest timezone UX

Severity: **Low**

The current web implementation deliberately omits a report timezone parameter, and `apps/iroha-web/src/lib/api.test.ts:196-202` locks that behavior. Older authoritative-looking text still says the web
owns timezone display and sends the browser timezone at `docs/plans/2026-08-12-iroha-data-cockpit-implementation.md:595-599` and `docs/plans/2026-08-12-periodic-reports.md:420-421`.

Smallest correction: update the plans/decision record to state that clients pick only a month while the server resolves the configured personal timezone, and retain timezone in the response for
semantic transparency rather than as a UI control.

### P-13 — the metric catalog advertises seven unsupported health series

Severity: **High**

The default registry publishes eight daily-health definitions at `apps/iroha-server/pkg/metrics/registry.go:61-68`. The metric-series dispatcher implements only `health.steps` at
`apps/iroha-server/pkg/metricseries/service.go:115-124`; every other health ID falls through to `ErrInvalidRequest` at `:161-163`.

Clients can therefore discover valid-looking catalog entries such as `health.hrv_sdnn` or `health.resting_hr`, then receive `400 invalid metric series request` for a request whose ID, grain, dates,
and dimensions satisfy the published definition. This violates the catalog's central promise and the registry-exhaustiveness acceptance in
`docs/plans/2026-08-12-world-in-data-cockpit-rework.md:90-95`.

Smallest correction: dispatch every registered daily metric through the daily source using an explicit metric-ID-to-canonical-key map, and add a table-driven test that executes at least one valid
request for every registry definition and supported grain.

### P-14 — report and metric APIs resolve omitted timezone differently

Severity: **High**

The report handler defaults an omitted timezone to configured personal time at `apps/iroha-server/pkg/httpapi/reports.go:11-16` (default Asia/Tokyo). The metric handler independently defaults to UTC
at `apps/iroha-server/pkg/httpapi/metrics.go:80-84`, while the web API helper always injects UTC when a caller omits it (`apps/iroha-web/src/lib/api.ts:513-523`). The expense route instead injects the
browser timezone (`apps/iroha-web/src/routes/expenses/+page.svelte:73-89` and `:103-118`).

The same selected month can therefore mean configured personal time, UTC, or the browser's current zone depending on surface. That is incompatible with a deterministic central cockpit after the
timezone control was removed, and will misalign activity/media series with report sections even after P-01 is fixed.

Smallest correction: make the server's configured personal timezone the default for every period API, let the web omit timezone consistently, and keep the resolved timezone in every response. Explicit
timezone remains available to machine clients that need it.

### P-15 — Kubernetes readiness does not check Iroha's required database

Severity: **Medium**

The only server health endpoint always returns `{status: ok}` without checking a dependency (`apps/iroha-server/pkg/httpapi/server.go:323-325`). The k3s Deployment uses that same endpoint for both
readiness and liveness (`harus-k3s/03-core/iroha/server.yaml:71-86`). A server with an unavailable or unmigrated Postgres instance is consequently marked Ready and receives cockpit traffic even though
every core data request fails.

Smallest correction: retain `/healthz` as process liveness, add `/readyz` with a bounded DB ping (and only genuinely required dependencies), use it for readiness, and test ready/not-ready transitions.

### P-16 — the documented broad k3s apply path is not reliable for Iroha

Severity: **Medium**

`harus-k3s/Makefile:74-75` applies every core YAML with client-side `kubectl apply`. Iroha includes a roughly 499 KB generated media-bridge ConfigMap, which cannot safely carry the client-side
last-applied annotation, and a fixed-name migration Job whose pod template becomes immutable when its image tag changes. The Iroha deployment README already requires deleting that Job before
reapplying it (`harus-k3s/03-core/iroha/README.md:105-118`).

This means `make apply-core`/`make apply-all` can fail partway and encourages a manual narrow apply sequence. Current audit state also illustrates the handoff risk: five manifests and two
version/status files are dirty at `.02`, while `.03` images were imported but deliberately not deployed.

Smallest correction: make the repository-owned apply path idempotent—use server-side apply or split/package the generated bridge data, and recreate or uniquely name the migration Job as an explicit
step. Add a narrow Iroha deploy target or checked playbook that validates all five image pins before mutation and reports a single atomic handoff state.

## Confirmed strengths

- **Canonical ownership is correctly domain-shaped.** The expense migration is one constrained typed table rather than EAV or a workflow graph
  (`apps/iroha-server/db/migrations/00007_expenses.sql:3-30`), while metrics are immutable application metadata above domain services (`apps/iroha-server/pkg/metrics/definition.go:11-35`). No
  intake/candidate/OCR table was introduced.
- **Expense ingestion has a sound deterministic core.** Validation preserves positive minor-unit money, bounded typed categories/items, and stable source identity
  (`apps/iroha-server/pkg/expenses/service.go:272-339`). Create uses a unique source identity plus normalized fingerprint and distinguishes created, identical retry, conflict, and tombstone
  (`:350-389`). Telegram, Suzuran, OCR, and confirmation are absent from this path.
- **Monthly reporting is server-owned and typed.** One orchestrator reads all five canonical domains and returns fixed typed sections (`apps/iroha-server/pkg/reports/monthly.go:24-64`). Period
  construction keeps half-open calendar and instant bounds explicit (`apps/iroha-server/pkg/reports/period.go:26-60`). No weekly endpoint, scheduler, report table, or Telegram delivery path was added.
- **The public/private boundary is still narrow.** `/api/v1` is documented as a private tailnet service, while the public surface remains a static sanitized activity projection
  (`docs/contracts/api-v1-decisions.md:8-12` and `:64-71`). The public-export regression test explicitly rejects expense/report leakage (`apps/iroha-server/pkg/publicexport/validate_test.go:20-31`).
- **The theme registry is a real component registry.** All six definitions point to theme-owned Expense and Report components rather than CSS class aliases
  (`apps/iroha-web/src/lib/themes/registry.ts:92-116`, `:142-182`, and `:207-252`). Controllers and domain data remain outside those compositions, which is the correct ownership direction even though
  P-03/P-08 leave the view model incomplete.
- **The shared frontend boundary is appropriately narrow.** Both web apps alias the source-only `@iroha/shared` package, and identical behavior such as StatTile is wrapped from it rather than
  duplicated. Private API clients and the theme registry remain app-owned (`packages/iroha-shared/README.md:1-9`).
- **Navigation no longer grows one top tab per domain/metric.** The grouped model separates primary, domain, analysis, and tool destinations (`apps/iroha-web/src/lib/navigation.ts:1-117`), and
  registry-owned menus close after selection (`apps/iroha-web/src/lib/components/NavigationMenu.svelte:14-34`). P-04 is an execution gap in metric discovery, not a reason to discard the grouped
  architecture.
- **The general CLI foundation is reusable and conventional.** It uses a single `requests.Session`, bounded timeouts, structured API errors, stdin/file JSON, and lossless JSON by default
  (`scripts/iroha_cli.py:15-90`). Extending this transport to the missing resources in P-10 does not require another client or agent workflow.
- **Static engineering gates are healthy.** Formatting, linting, unit tests, route/OpenAPI examples, Svelte diagnostics, and production builds all pass. P-11 concerns missing runtime gates, not a
  broken baseline toolchain.

## Unverified risks and audit limits

- DB-backed integration tests were inspected but not executed because their target starts the stopped local Podman database stack. Their presence is not counted as a pass.
- The latest code was not deployed and no exhaustive browser matrix was run. Live k3s remained on `.02`; prepared `.03` images were intentionally left unused.
- No `EXPLAIN ANALYZE`, one-/ten-year series benchmark, or monthly-report p95 measurement exists for the audit fixture, so no materialized read model is justified and no latency claim is made.
- The four requested Sol xhigh reviews were terminated at the quota checkpoint without results. This report is therefore a complete primary source audit, not a completed independent-adversarial
  review.
- Passing static review cannot prove that all historical imported data is semantically correct. The release fixture must include real boundary and missing-data cases before Gate C.

## Release decision and corrective sequence

**Decision: NO-GO for v0.4 production and Gate C.** The architecture should not be discarded, and no database redesign is warranted. The release is blocked by ten concrete High findings at the
semantic API, controller, representation, CLI, and verification layers.

The smallest credible corrective sequence is:

### Gate R0 — freeze the remaining product contract

1. Make configured personal timezone the one default for reports and metric series; web controls select periods, not timezones.
2. Freeze the v0.4 CLI resources. Recommended minimum: existing expense/report/ metric commands, `import file` over the stable raw-file/import API, and read-only activity, sleep, daily-health, and
   media wrappers. Do not add new canonical write APIs merely for symmetry.
3. Define the report visual model explicitly: one honest domain panel per available section plus a cross-domain availability/coverage summary; never compare incompatible units on one magnitude axis.
4. Update the superseded timezone and CLI paragraphs before implementation so code is not forced to choose between conflicting plans.

### Gate R1 — repair server semantics first

1. Implement every published metric definition or remove it from the catalog; add executable registry-contract tests (P-13).
2. Separate instant conversion from calendar-date bucketing and cover positive and negative timezone offsets across month boundaries (P-01).
3. Resolve omitted metric timezone through server config and make web clients omit it consistently (P-14).
4. Run DB-backed exact-value tests for every metric, monthly section, empty period, observed zero, currency/category dimension, tombstone, and repeated byte-stable request.

### Gate R2 — make route state truthful and addressable

1. Wire and test MonthNavigator keyboard behavior (P-02).
2. Make expense/report month and expense filters validated URL state, including refresh, direct link, and browser back/forward (P-05).
3. Add cursor/load-more behavior and an incomplete-list indicator for ledgers over 50 records (P-06).
4. Commit multi-request results atomically or maintain explicit per-panel period/status; never retain a prior-period chart after a failed request (P-09).
5. Add out-of-order-response tests for rapid month/filter navigation.

### Gate R3 — finish representation and discovery

1. Build cross-domain report visuals from server series/typed sections and keep the exact details below them (P-03).
2. Turn catalog discovery into actual searchable navigation and a metric-series viewer; a metric deep link must select and render that metric (P-04).
3. Key expense category colors by semantic category through each theme rather than ranking index (P-07).
4. Wire chart/table parity, metadata, coverage, source/method, and CSV download; delete disconnected primitives instead of keeping ceremonial code (P-08).
5. Add the frozen multi-resource CLI surface using the existing transport (P-10).

### Gate R4 — make verification match the product

1. Add a release-candidate target that runs DB integration tests and production builds against deterministic seeded data (P-11).
2. Run browser assertions—not screenshot generation alone—over expenses, reports, Patterns metric deep links, and shared period controls for all six registry themes in light and dark.
3. Include empty, partial, multi-currency, more-than-50-expense, timezone-edge, failed-series, and real cross-domain months. Assert chart values, details, source metadata, URL state, keys, menus,
   console errors, and theme markers.
4. Measure one- and ten-year series plus monthly report p95 before changing the database. Keep on-demand aggregation if the documented SLOs pass.

### Gate R5 — harden and release deliberately

1. Add DB-aware `/readyz` and point Kubernetes readiness to it (P-15).
2. Make the Iroha k3s apply/migration path idempotent and validate all five image pins as one handoff (P-16).
3. Rebuild one fresh dev tag after R0-R5, import it, run server-side dry-run and migration rehearsal, deploy only the narrow Iroha resources, and verify API, seeded charts, reports, public-export
   exclusion, jobs, and rollback.
4. Request owner Gate C approval only after the evidence above is attached. Do not deploy the already prepared `.03` images.

Gate C is ready for review only when all ten High findings are closed, Medium deferrals (if any) are explicit, `make validate` and DB integration pass, every catalog metric executes, and the complete
six-theme browser matrix passes with real seeded data.
