# Apple Health provider capabilities

Status: full-export ingestion implemented end to end. The bounded Shortcut path is implemented on the **receiving** side only -- the endpoint, envelope contract, and import behavior exist and are
fixture-verified, but no on-device producer has been built, so no `iroha.health.shortcut.v1` payload has yet been generated by an iPhone. Physical-device transport testing is deferred operational
hardening.

## Evidence

Apple Health is ingested as a full export ZIP containing `export.xml` and route files. The export is treated as a complete snapshot and reconciled by stable provider source identity plus content hash.

The automatic path accepts the versioned `iroha.health.shortcut.v1` JSON envelope at `POST /api/v1/intake/health`. It is authenticated with the deployment-scoped `IROHA_HEALTH_INTAKE_TOKEN`, stores
the unchanged payload as raw evidence, and queues a normal import job. Shortcut coverage is bounded and uses `bounded_replacement`: partial windows never imply that older records should be deleted.

## Acceptance boundary

- Full exports retain complete-snapshot reconciliation semantics.
- Shortcut payloads retain raw evidence and create source coverage assertions in the same transaction as canonical observations.
- Duplicate evidence is skipped at the import-job boundary; changed or late bounded windows create a new snapshot without deleting records outside the bounded evidence.
- Coverage completeness is recorded evidence, not a replacement instruction. `covered` and `partial` are stored and behave identically today: a bounded window never deletes canonical rows inside it,
  so a record deleted or corrected in Apple Health does not propagate until the owning evidence is replayed.
- `unknown` completeness is accepted end to end -- a source that cannot prove it read the whole window (locked phone, ambiguous permission) is representable rather than rejected after a `202`.
- v0.5 accepts complete original-export replay for data fidelity and the authenticated `iroha.health.shortcut.v1` fixture probe for automatic intake behavior. A seven-day physical-device trial (locked
  phone, missed day, offline delivery, and permission/empty-state behavior) remains useful post-v0.5 operational hardening, but is not a v0.5 release gate.
- Producing the envelope on-device is unproven. Apple's Shortcuts has no health-sample-to-JSON action, so the payload must be hand-built in a `Repeat with Each` loop, and `daily_summaries` needs
  Activity ring _goals_, which come from `HKActivitySummary` rather than any `Find Health Samples` type. Confirm what a real producer can emit before treating the envelope's optional sections as
  supplied. [Health Auto Export](https://help.healthyapps.dev/en/health-auto-export/automations/) is the leading alternative producer: it already POSTs JSON to a custom REST endpoint, which would need
  its own adapter rather than this envelope.
